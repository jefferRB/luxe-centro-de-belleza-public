# Media publication policy

Photos of clients, their work and the premises belong to the business and to the people in
them. Showing them on the live site does not grant the right to redistribute the files. This
repository therefore contains **no client media**.

## Policy (enforced in code)

Each catalog record carries its own permission (`src/data/media-catalog.ts`):

| Status | Meaning | `astro dev` | Build |
|---|---|---|---|
| `approved` | Client media with recorded written authorization (`evidence` and `reviewedAt` required) | shown | shipped |
| `demo` | Redistributable demonstration media made for this repository (`provenance` and `license` required) | shown | shipped, and the page states that images are illustrative |
| `local-preview` | Client media still under review | shown, with a notice | **never** |
| `pending`, `third-party` | Not usable | never | never |

Promotional material is never shown, whatever its status. No list, flag or environment
variable can widen a record's permission. The production site's earlier deployment list
(which published `local-preview` media) was removed in this version.

Enforcement points:

- `canUseMedia` / `canUseVideo` / `canShow` decide what each mode renders.
- `scripts/verify-build.ts` fails the build if a non-publishable file name or reference appears in
  the output, if a shipped record lacks approval or demo provenance, or if demo media is shown
  without the on-page notice.
- `tests/media-policy.test.ts` fails if any image or video in the repository is not a generated
  demo file whose SHA-256 is recorded in `src/assets/demo/manifest.json` (or one of the generated
  site icons), and if archives, environment files or private document folders are present.
- `tests/media.test.ts` covers each status and the empty states a build shows when nothing is
  approved.

## Demo media

`src/assets/demo/` is generated by [`scripts/generate-demo-media.ts`](../scripts/generate-demo-media.ts):

- vector illustrations drawn in code with the site palette (emerald, gold, ivory, ink);
- no photography, no client imagery, no logos and no third-party material;
- the same ids, categories and aspect ratios as the originals they replace, so the globe, the
  works crown and the space tour lay out exactly as on the production site;
- every image carries a "DEMO · ILUSTRACIÓN DE DEMOSTRACIÓN" label (focal framing can crop it in
  small panels, so every alt text also starts with "Ilustración de demostración" and the footer
  states that the images are illustrative);
- two short silent WebM loops (VP9) for the globe's video cards, encoded from generated frames.

Regenerate with `npm run demo-media` (set `FFMPEG_PATH` to an ffmpeg with `libvpx-vp9` to
re-encode the loops). The script records each file's SHA-256 in `manifest.json`.

The favicon set and `public/og-image.jpg` are generated from a neutral demo mark
(`public/favicon.svg`) and the demo reception illustration (`npm run favicons`, `npm run og-image`).

## README images (`showcase/`)

The screenshots and loops in the README are captured by
[`scripts/capture-showcase.ts`](../scripts/capture-showcase.ts) from the **local demo build**
(`dist/client` served on loopback), never from the production site, so they can only contain demo
media. The script records their hashes in `showcase/manifest.json`; the leak guard rejects any
other image in that folder. The cover adds a line stating that illustrations replace the studio's
photography.

## Using real media in a deployment

Add the files outside version control or in a private fork, give each record an `approved`
permission with the evidence reference and review date, and keep `local-preview` for anything
still waiting for consent.
